# 브랜치 전략 및 배포 정책 (사내 공통 정책 발췌)

이 문서는 커머스플랫폼팀뿐 아니라 개발실 공통으로 적용되는 Git/배포 정책을 이 저장소 맥락에 맞게 정리한 것입니다. 전사 공통 원본은 사내 위키 `개발실 > 협업 정책`에 있으며, 충돌 시 위키가 원본입니다.

## 1. 브랜치 전략

```
main        운영 배포 브랜치. 항상 배포 가능한 상태 유지
develop     스테이징 통합 브랜치. 다음 배포 대상 기능이 모임
feature/*   신규 기능 개발 (예: feature/order-partial-cancel)
fix/*       버그 수정
hotfix/*    운영 장애 긴급 수정 (main에서 분기, main과 develop에 모두 병합)
release/*   배포 준비 브랜치 (QA 기간 동안 유지, 선택적으로 사용)
```

- `feature/*`, `fix/*`는 `develop`에서 분기하고 `develop`으로 병합합니다.
- `hotfix/*`는 `main`에서 분기하며, 병합 후 반드시 `develop`에도 cherry-pick 또는 merge로 반영합니다(반영 누락 시 다음 배포에서 버그가 재발합니다).

## 2. 커밋 메시지 규칙

```
[도메인] 요약 (50자 이내)

- 상세 변경 사항 (필요 시)
- 관련 이슈: JIRA-1234
```

도메인 태그 예: `[order]`, `[payment]`, `[product]`, `[infra]`, `[docs]`. 여러 도메인에 걸치면 `[order/payment]`처럼 표기합니다.

## 3. PR 규칙

- PR 제목은 커밋 메시지 규칙과 동일한 형식을 따릅니다.
- PR 템플릿 필수 항목: 변경 요약, 영향 받는 서비스, 테스트 방법, 롤백 방법
- **승인 요건: 코드오너 1인 + 도메인 담당자 1인, 총 2 approve.** 결제/정산처럼 금전 영향이 있는 변경은 파트장 승인이 추가로 필요합니다.
- Draft PR 단계에서도 CI(빌드/테스트/린트)는 통과해야 리뷰 요청이 가능합니다.
- `main`, `develop` 브랜치에 직접 push는 저장소 설정으로 차단되어 있습니다(Branch Protection).

## 4. 배포 정책

- 운영 배포는 **배포 캘린더(사내 위키)에 사전 등록** 후 진행합니다. 등록 없는 배포는 원칙적으로 금지됩니다.
- 배포 가능 시간대: **평일 오후 2시 ~ 5시**. 이 시간대를 벗어난 배포는 파트장 승인이 필요합니다.
- **금요일 및 공휴일 전날 배포는 지양**합니다(주말 장애 대응 인력 부족). 불가피한 경우 온콜 담당자에게 사전 공유합니다.
- 배포는 ArgoCD를 통한 GitOps 방식이며, `main` 병합 → 이미지 빌드(GitHub Actions) → 매니페스트 레포 업데이트 → ArgoCD 자동 동기화 순서로 진행됩니다.
- 배포 후 15분간 에러율/응답시간 대시보드를 담당자가 직접 모니터링합니다(자동 롤백 임계값: 5xx 비율 5% 초과 시 자동 롤백).

## 5. 핫픽스 절차

1. 장애 인지 즉시 Slack `#commercehub-incident` 채널에 상황 공유
2. `main`에서 `hotfix/*` 브랜치 생성, 최소 변경으로 수정
3. 리뷰는 1인 승인으로 완화 가능(단, 사후에 정식 리뷰 진행)
4. 배포 후 `docs/incident-response.md` 절차에 따라 장애 리포트 작성

## 6. 코드 오너

`CODEOWNERS` 파일 기준으로 서비스별 코드오너가 지정되어 있으며, 코드오너는 최소 2주 전에 변경을 팀에 공지해야 교체할 수 있습니다.
